# 从 Vibe Coding 到 Agentic Engineering：产品经理如何与 AI 做出真正可用的产品

## AI 让做出 Demo 变得很容易

今天，即使完全不会编程，一个产品经理也可以用自然语言告诉 AI：

> 帮我做一个多 Agent 协作平台。用户可以选择 Agent、发起任务、查看执行过程，并在需要时进行确认。

不久之后，一个看起来相当完整的系统就会出现在眼前：它有页面、有按钮、有任务列表，甚至真的能够调用 Agent。

这是 Vibe Coding 最令人兴奋的地方。它大幅降低了把想法变成软件的门槛，让产品经理和业务人员可以跳过漫长的资源协调，直接验证自己的构想。

但这也容易制造一种错觉：

> 既然 AI 已经做出了一个能运行的版本，距离真正投入使用应该不远了。

实际情况往往不是这样。

AI 非常擅长快速做出一个**看起来成立的验证版本**，却不会自动把它变成一个可靠产品。Demo 只需要证明“这件事似乎可以实现”，真正投入使用的产品还必须回答：

- 异常发生时会怎样？
- 任务什么时候才算真正完成？
- 用户中途改变要求怎么办？
- 数据和文件保存在哪里？
- 外部服务断开后如何恢复？
- 哪个模块负责做决定，哪个模块只负责执行？
- 新功能会不会破坏原有流程？

如果这些问题没有被明确，项目很容易停留在“小玩具”阶段：第一次体验很惊艳，一进入真实、复杂、长时间运行的场景，就不断暴露问题。

Vibe Coding 并没有失去价值。它仍然非常适合探索想法、制作原型和验证交互。真正需要摒弃的是把它误认为完整的软件交付方法：

> Vibe Coding 就是用一句话让 AI 帮你生成整个项目。

一句话可以生成项目的起点，却很难生成产品的终点。

当 AI Agent 开始自主阅读项目、制定计划、修改文件、运行测试并持续完成开发任务，这种方式通常被称为 **Agentic Coding**。当我们进一步用明确需求、工程约束、分阶段实施和验收证据来管理这些 Agent，目标从“生成代码”转向“交付可靠产品”时，它更接近 **Agentic Engineering**。

这并不是一次单纯的概念升级，而是工作方式的变化：

- Vibe Coding 关注“我能否快速把想法做出来”。
- Agentic Coding 关注“Agent 能否自主完成开发任务”。
- Agentic Engineering 关注“人和 Agent 如何共同交付可维护、可验证、可投入使用的产品”。

## 我们是如何意识到这一点的

我们曾用 AI 开发一套多 Agent 协作产品 TeamRoom。它的目标是让用户能够向主要助手发起任务，观察多个 Agent 的协作过程，并在需要时进行人工确认。

第一版很快就运行起来了。但随着测试深入，我们逐渐发现：

- 不需要人工确认的内容也可能弹出确认框。
- 子 Agent 仍在执行，系统却判断任务已经结束。
- 用户只是想进行一次普通对话，系统仍强制进入派发和审核。
- 为了解决某个问题加入的新规则，又可能干扰其他流程。
- 历史信息不断堆入提示词，模型越来越慢。

这些问题单独看都可以继续修复。但我们逐渐意识到，真正的问题并不是某几行代码写错了，而是产品边界没有被定义清楚。

TeamRoom 究竟应该负责什么？

它是一个负责规划、派发和审核的工作流引擎，还是一个连接用户与 Agent 的协作界面？如果 Agent 本身已经具备任务拆解和调用子 Agent 的能力，TeamRoom 再做一套调度，就会形成两个控制中心。

于是，我们暂停了继续打补丁，重新从产品需求开始梳理。最终确定：

> Agent 决定如何完成任务，TeamRoom 负责中转、展示、人工介入和状态恢复。

这个边界一旦明确，很多问题不再需要增加规则解决，反而可以通过删除错误职责来解决。

这次经历让我们意识到：**Vibe Coding 降低了原型实现成本，Agentic Coding 提高了执行自动化程度，但只有进入 Agentic Engineering，需求定义、系统边界和验收判断才会成为整个过程的正式组成部分。**

## 从 Vibe Coding 走向 Agentic Engineering

把一句需求交给 AI，等待它生成完整项目，更像是在抽取一个可能符合预期的答案。

Agentic Engineering 更接近一个有明确输入、约束和验收的循环：

```text
提出想法
-> 澄清需求
-> 明确边界
-> 设计流程
-> 分阶段实现
-> 真实验证
-> 发现问题
-> 沉淀规则
-> 继续迭代
```

AI Agent 可以在这个过程中扮演产品访谈者、方案设计者、开发者、测试者和审查者。但产品经理必须控制方向、约束和验收标准。

### 第一步：先让 AI 提问，不要急着写代码

需求越模糊，AI 可以自由推断的空间越大。它做出的第一版也许符合你的想象，但那些未经讨论的细节，最终都会以问题的形式回来。

开始一个项目时，可以先这样与 AI 交互：

```text
我想设计一个【产品概念】。

请先不要写代码，也不要直接给出完整方案。
你先扮演产品经理，每次向我询问一个最关键的问题，
帮助我依次明确用户、场景、产品边界、核心流程、
异常处理、数据归属和验收标准。

如果我的回答与之前的决定冲突，请明确指出。
等需求完整后，再帮我整理产品需求文档。
```

这看起来会让开发开始得更慢，实际上却能显著减少后期无休止的修补。

### 第二步：先定义谁负责什么

很多 AI 项目的复杂度并不是功能太多，而是多个模块在做同一件事。

例如：

- AI Agent 和应用程序都在判断下一步。
- 前端和服务端都在推测任务状态。
- 新逻辑和兼容逻辑都在处理同一条消息。
- 产品希望 AI 自主决策，又同时通过固定流程限制它。

在设计功能前，应该先回答：

- 产品负责什么？
- AI Agent 负责什么？
- 外部平台负责什么？
- 用户必须在哪些节点做决定？
- 哪些事情产品明确不做？

“不做什么”往往比功能列表更能决定产品能否长期维护。

### 第三步：分阶段实现，不要一次生成整个系统

一次性要求 AI 完成整个项目，会把需求理解、架构设计、代码实现和测试混在一起。即使最终能运行，产品经理也很难知道内部做出了哪些假设。

更好的方式是每次只完成一个可验收阶段：

```text
请实现当前计划中的这一阶段。

本轮只处理：
- …
- …

本轮不要处理：
- …
- …

请沿用现有项目结构。完成后告诉我：
1. 修改了什么；
2. 验证了哪些场景；
3. 哪些内容尚未实现；
4. 是否发现与既有需求冲突的地方。
```

让每一轮修改都有清晰边界，项目才不会在连续对话中逐渐偏离最初目标。

### 第四步：把真实使用当成需求发现过程

产品经理不一定能读懂代码，但可以观察真实行为。

在 TeamRoom 的测试中，很多关键需求都不是从代码中看出来的，而是在使用中发现的：

- 用户补充一句要求，系统为什么把它当成新任务？
- Agent 已经提出问题，为什么用户没有看到确认卡？
- 服务重连后，为什么任务耗时重新开始？
- 子 Agent 仍在运行，为什么界面已经显示完成？

这些现象不能只作为一个个孤立 Bug 处理。产品经理需要继续追问：

> 这个问题暴露的是一个局部错误，还是系统缺少一条通用规则？

例如，“任务提前完成”不应该通过多等几秒来解决，而应该明确任务完成必须满足哪些条件。

一个好的修复不仅让当前例子通过，还应该能够解释并约束一整类场景。

## 如何避免需求漂移和越改越乱

AI 开发的速度很快，因此需求漂移也会发生得更快。

一次局部修改可能悄悄引入新流程；一个临时兼容方案可能逐渐变成长期架构；旧需求与新需求可能同时存在于代码和提示词中。

我们认为有三种方法尤其重要。

### 1. 维护一份“当前真相”

不要让聊天记录成为项目唯一的需求文档。

项目需要持续维护一份简明现状，包括：

- 产品定位和边界。
- 当前架构。
- 已完成能力。
- 尚未解决的问题。
- 关键决策。
- 下一阶段计划。

每次重要修改都要与它核对。新结论应该覆盖旧结论，而不是不断叠加。

### 2. 修改前先判断影响面

可以要求 AI 在动手前先回答：

```text
在修改前，请先说明：
1. 当前问题的直接原因；
2. 它属于显示问题、状态问题还是架构边界问题；
3. 修改会影响哪些正常和异常流程；
4. 是否与之前确认的产品边界冲突；
5. 需要增加哪些回归测试。

不要只针对当前示例添加特殊判断。
```

这能把 AI 从“立即修复眼前现象”切换到“理解系统后再修改”。

### 3. 把重要问题变成测试

已经确认过的产品规则，不应该只保存在人的记忆和对话历史中。

例如：

- 简单问题不应强制进入复杂工作流。
- 用户补充要求不应创建重复任务。
- 等待用户回答时，任务不能自动继续。
- 子任务未结束时，主任务不能显示完成。
- 服务重连不能重新发送原任务。

这些都可以转化成自动化测试。测试不仅在检查代码，也在保存产品已经达成的共识。

## 四套可以直接复用的工具

### 一、需求澄清问题清单

在让 AI 开始实现前，至少回答以下问题：

#### 用户与场景

- 谁是核心用户？
- 用户真正要完成什么任务？
- 用户最不能接受的失败是什么？

#### 产品边界

- 产品负责什么？
- AI Agent 负责什么？
- 外部平台负责什么？
- 哪些事情明确不做？

#### 核心流程

- 用户从哪里开始？
- 第一步由谁处理？
- 哪些步骤必定发生，哪些只是可选？
- 谁决定进入下一步？

#### 状态与异常

- 有哪些关键状态？
- 什么证据代表任务真正完成？
- 用户不回复、服务断线或状态未知时怎么办？
- 哪些事情绝对不能由系统自动决定？

#### 人工介入

- 哪些情况必须询问用户？
- 用户能否中途补充、停止或改变方向？
- 用户回答应该返回给哪个角色和会话？

#### 验收

- 最核心的成功场景是什么？
- 最危险的异常场景是什么？
- 如何证明功能真的完成，而不是页面看起来完成？

### 二、项目边界模板

```markdown
# 产品名称

## 一句话定位
这个产品是……

## 核心用户与场景
- 核心用户：
- 使用场景：
- 用户目标：

## 产品负责
- …
- …

## 产品不负责
- …
- …

## 角色与责任
- 用户：
- 本产品：
- AI Agent：
- 外部平台：

## 核心流程
用户输入
-> …
-> …
-> 用户获得结果

## 完成条件
只有满足以下条件，任务才算完成：
- …
- …

## 异常与恢复
- 用户未回复时：
- 外部服务断开时：
- 状态未知时：

## 首版验收标准
- …
- …
```

### 三、与 AI 交互的提示词

#### 需求阶段

```text
先不要写代码。请每次只问我一个关键问题，
帮助我明确用户、场景、边界、流程、异常和验收标准。
发现前后决定冲突时，请主动指出。
```

#### 设计阶段

```text
请基于已确认需求，检查职责重叠、状态缺失和无法验收的描述。
然后给出核心对象、流程、状态、外部系统边界和分阶段计划。
先输出设计，不要修改代码，也不要增加未经确认的新流程。
```

#### 实现阶段

```text
请只实现本轮明确列出的范围，沿用现有项目结构。
完成后说明修改内容、验证场景、剩余工作和潜在冲突。
```

#### 验收阶段

```text
请暂停增加功能，以产品审查和测试的视角检查当前实现。
重点检查异常恢复、重复提交、长任务、用户中途介入、
外部服务断线和任务完成判断。
优先报告可能导致错误结果或用户误判的问题。
```

### 四、“暂停打补丁，转向重构”的判断标准

如果以下现象出现三项以上，就应该暂停新增功能，重新检查需求和架构：

1. 同类问题在不同场景中反复出现。
2. 一个修改需要绕过多套旧逻辑。
3. 两个模块或角色在做同一件事。
4. 简单任务也必须经过复杂流程。
5. 状态越来越多，却无法清楚解释完成条件。
6. 系统依赖模型措辞或文本关键词判断流程。
7. 提示词和历史上下文随轮次持续膨胀。
8. 维护者已经无法用一张图解释当前流程。
9. 每次修复只能为当前例子增加特殊判断。
10. 修改一个功能总会破坏多个原有功能。

重构不是全部推倒重写。更稳妥的方式是冻结旧逻辑、重新确认边界、建立新链路，再通过测试逐步迁移。

## 产品经理在 Agentic Engineering 中承担什么角色

Agentic Engineering 不要求产品经理成为程序员，但它要求产品经理更直接地参与软件形成过程。

产品经理至少承担四个角色。

### 问题定义者

AI 能够非常快速地实现错误方向。产品经理必须先定义真正值得解决的问题。

### 边界设计者

产品经理需要判断用户、产品、Agent 和外部平台分别负责什么。许多所谓的技术复杂度，实际来自职责重叠。

### 协作与上下文管理者

产品经理需要控制什么时候提问、什么时候设计、什么时候实现、什么时候暂停测试，并维护一份不会随对话漂移的项目现状。

### 验收与决策者

AI 可以写代码和测试，但仍由产品经理判断产品是否真的解决了用户问题，以及速度、体验、复杂度和可靠性之间应该如何取舍。

## 结语：从“生成代码”走向“交付产品”

Vibe Coding 的重要价值，是让更多人能够在很短时间内把想法变成可见、可操作的验证版本。Agentic Coding 又进一步让 AI Agent 能够承担更完整的开发任务。

但从验证版本到真正投入使用，仍然需要清晰的需求、稳定的边界、异常处理、持续测试和真实验收。这正是 Agentic Engineering 要解决的问题。

过去，这些工作由产品、设计、研发和测试团队共同完成。现在，AI 可以承担其中大量执行工作，但不会自动替人做出全部产品判断。

所以，Agentic Engineering 的核心不是找到一句无所不能的提示词，也不是把整个项目完全交给 Agent，而是建立一种可控制、可验证的新协作方式：

> AI 负责快速实现、反馈和验证，产品经理负责持续澄清、控制边界、维护共识并做出最终判断。

Vibe Coding 可以快速做出一个令人惊喜的原型，Agentic Coding 可以让 Agent 承担越来越完整的开发工作。

而如何把这些能力组织起来，形成真正有人愿意长期使用的产品，才是 Agentic Engineering 最值得产品经理学习的部分。
