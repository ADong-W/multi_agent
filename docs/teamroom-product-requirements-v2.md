# TeamRoom V2 产品需求

状态：已完成需求与界面确认，进入技术设计阶段。

## 1. 产品定位

TeamRoom 是 OpenCode 或 OpenClaw 上方的协作界面与控制层。

它负责：

- 将用户消息交给主要助手。
- 展示主要助手及其原生调用的协作助手。
- 转发流式输出、问题、权限申请和文件变化。
- 允许用户在运行中补充要求、停止任务或纠正方向。
- 在连接异常后恢复展示真实状态。
- 管理 TeamRoom 自己创建的会话、任务、文件索引和权限偏好。

它不负责：

- 强制执行“分析、派发、审核”等固定流程。
- 替主要助手拆解业务需求。
- 解析并执行 Supervisor 返回的派发计划。
- 自动补全或校验 Agent 的业务 Payload。
- 将房间历史、完整 SOP 或重连信息重复注入 Agent 提示词。
- 管理由 TeamRoom 之外创建的底座会话。

## 2. 核心原则

1. **Agent 决定工作流**：主要助手决定直接回答还是调用协作助手。
2. **TeamRoom 只做中转与观察**：不在 Agent 之外增加业务步骤。
3. **Human in the loop**：问题、权限和运行中纠正必须及时到达用户。
4. **底座原生优先**：使用 OpenCode/OpenClaw 原生会话、事件、提问、权限和中断能力。
5. **状态未知不等于完成**：Compaction、断线、超时或存在文本均不能单独证明任务完成。
6. **上下文最小化**：优先依赖同一底座会话的原生上下文，只传递当前动作必需信息。
7. **泛化优先**：不得依赖 FoxAgent 固定角色名、固定 Agent 数量或固定业务 SOP。

## 3. 运行服务与首次启动

首次启动弹出连接设置，默认选择 OpenCode，也可选择 OpenClaw。

### 3.1 连接方式

- macOS/Windows：
  - TeamRoom 启动本机运行服务。
  - 连接已经运行的本机或远程服务。
- Linux 首版：
  - 仅连接已经运行的服务。

连接失败时停留在设置界面，展示可理解的诊断，不自动切换其他底座。

### 3.2 文件区

- 检测到项目 `input/`：默认使用项目文件区。
- 用户可切换为 TeamRoom 默认文件区，并可恢复使用项目文件区。
- 未检测到项目 `input/`：自动创建并使用 TeamRoom 默认文件区，不要求用户输入路径。
- TeamRoom 只管理上传、索引、预览和下载；备份、`working/`、`output/` 等业务目录由 Agent 自己的 SOP 管理。

### 3.3 连接档案

一个连接档案保存：

- 底座类型和地址。
- 本机启动方式或远程连接方式。
- 认证信息的安全引用。
- 文件区设置。
- TeamRoom 权限偏好。
- 支持能力探测结果。

协作室创建后绑定一个连接档案和工作区。

## 4. 协作室与成员

- 用户从底座可用 Agent 中选择协作室成员。
- 第一个加入的 Agent 默认成为主要助手，用户可以更换。
- 主要助手负责接收普通用户消息。
- 用户可以直接打开其他 Agent 的独立对话；该对话默认是单 Agent 对话，不参与主要协作链。
- 成员列表同时是允许调用的 Agent 范围。
- 底座支持强约束时直接阻止越权调用；不支持时进入监测模式，发现越权后尽可能中止并暂停父任务。

## 5. 对话、任务与调用

### 5.1 层级

```text
协作室
  -> 对话
    -> 用户任务
      -> 主要助手运行
        -> 原生协作助手调用
```

- 每条普通用户消息创建一个新任务。
- 回答问题、处理权限或补充指导时，继续同一个任务。
- 同一对话复用对应底座会话。
- 用户可在任务结束后继续当前对话，无需新建对话。

### 5.2 任务开始

用户消息直接发给主要助手。TeamRoom 不预先创建：

- Supervisor Dispatch
- Payload Correction
- Specialist Stage
- Supervisor Review

只有底座真实发生的调用才显示为协作步骤。

### 5.3 上下文

TeamRoom 不无脑拼接历史。

协作助手应获得：

- 当前用户目标。
- 主要助手本次调用的原生指令或 Payload。
- 已完成上游工作中与当前任务相关的简短结果。
- 必要文件引用。
- 尚未解决且与当前动作相关的用户决定。

不应获得：

- 完整房间历史。
- 重复 SOP。
- 重连、轮询、心跳等系统信息。
- 已被新结论覆盖的旧确认内容。
- 与当前动作无关的 Agent 输出。

上下文超限时只提示用户和记录风险，不由 TeamRoom擅自改写业务信息。

## 6. 流式过程与任务结束

### 6.1 流式展示

- Agent 可见文本以左侧对话气泡持续展示。
- 工具调用和过程信息归入可折叠的“处理过程”。
- Agent 正在回复时过程展开；产生最终回复后自动收起，显示处理耗时。
- 单个过程气泡达到展示上限时自动收起，并继续生成新的过程气泡，不截断底座数据。
- 最终回答使用普通 Agent 对话气泡，不放在中间灰色系统框。

### 6.2 完成判定

任务完成必须同时满足：

- 主要助手底座运行明确进入完成或 idle。
- 所有由该任务产生的协作助手调用均已完成、失败或取消。
- 没有待处理的问题、权限、工具调用、重试或恢复核对。
- 没有正在进行的 Compaction。

如果主要助手已 idle 且所有子调用结束，但没有最终总结，则标记：

> 运行已结束，未生成最终总结

用户仍可在同一对话继续交流。

### 6.3 后台审计

当主要助手明确输出可交付结论并进入后台审计阶段时：

- 前台先展示结论。
- 用户可见的任务等待计时停止。
- 审计作为后台活动继续记录。
- 审计发现新问题时重新激活原任务并弹出确认或风险提示。

## 7. 用户介入

### 7.1 结构化确认

- 原生问题和严格结构化 `confirmation_points` 均展示为卡片。
- 一个确认对象对应一张卡片。
- 不按照问号、分号、序号或换行拆分问题。
- `question` 作为标题或主要问题。
- `hint` 作为辅助说明。
- `options` 原样作为选项。
- 多个问题允许部分填写后统一提交。
- 答案返回提出问题的 Agent、会话和请求，不广播给其他 Agent。

### 7.2 权限

OpenCode 权限申请实时转发。

用户可选择：

- 拒绝。
- 仅本次允许。
- 对当前连接档案始终允许同类操作。

信任规则只保存在 TeamRoom，对 TeamRoom 发起的会话生效，不修改底座全局设置。权限超时可继续等待或拒绝，绝不自动允许。

### 7.3 运行中指导

- 默认发送给主要助手。
- 可手动切换到当前协作助手。
- “补充要求”继续当前任务。
- “停止并重新说明”先中断整条调用链，确认中断后以新说明创建后续任务。
- 已完成的文件修改不会自动撤销，界面必须提前说明。

## 8. 异常恢复

### 8.1 自动恢复

断线后：

- 保留断线前累计耗时和阶段开始时间。
- 不把重连当作用户回复。
- 不重新发送任务。
- 通过事件游标、会话快照和底座状态核对恢复界面。

### 8.2 手动操作

- **重连运行服务**：恢复与底座的连接。
- **检查当前任务**：读取当前对话与调用链的真实状态。

两者必须在不同位置和文案下呈现。

### 8.3 特殊状态

- Compaction：显示为“正在整理上下文”，不是完成。
- 状态未知：显示“正在核对”，不自动进入下一步。
- 恢复后发现待确认问题：恢复原卡片，不生成空回复。
- 底座会话不存在：标记不可恢复并保留只读历史。

## 9. 文件与并发

### 9.1 文件

TeamRoom 展示：

- 用户上传文件。
- Agent 声明的文件。
- 实际检测到的新增或修改文件。
- 文件来源、修改 Agent、时间、预览和下载入口。

### 9.2 并发

- 默认按工作区串行。
- 可配置允许并行。
- 每个任务声明或推断读写范围。
- 写入范围不冲突时可并行。
- 写入范围冲突时按队列等待。
- 范围未知时锁定整个工作区。
- 等待用户确认的任务只保留自己的写锁；不冲突任务可继续。
- 队列默认 FIFO，用户可手动提高优先级。

## 10. 界面信息架构

### 左栏

- 当前连接与重连。
- 协作室。
- 协作成员。

### 中栏

- 对话选择。
- 当前任务状态与总耗时。
- 用户、主要助手和协作助手消息。
- 流式过程、确认卡、权限卡和异常恢复卡。
- 补充要求与停止纠正。

### 右栏

默认展开，可折叠。顺序为：

1. 当前进展。
2. 文件。
3. 用时。
4. 历史任务。

## 11. 首版验收标准

- 简单问答不会出现虚构的派发或审核步骤。
- 主要助手原生调用协作助手时，TeamRoom 能显示真实调用关系。
- OpenCode 原生问题和权限可在 TeamRoom 完成回答。
- Compaction、断线和流式文本不会触发错误完成。
- 重连后累计耗时不归零。
- 用户确认与自动重连同时发生时，不会生成空回答或继续错误任务。
- Agent 未明确结束时，TeamRoom 不进入下一任务。
- 多轮任务不会随着轮数线性重复注入全部历史。
- 最终回答始终位于对话流，系统状态位于状态区域。
